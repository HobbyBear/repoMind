# RepoMind 渐进式查询上下文评测

日期：2026-09-30

## 目标

在不接入 Kompress、向量库、RepoMind CLI、生成索引或外部图谱的前提下，借鉴 Headroom 的渐进式压缩思想优化 `repomind-query`：

1. 先路由少量候选文件。
2. 按问题只投影相关章节和 trouble 判断分支。
3. 未读取内容保留为 `文件路径#标题` 详情句柄。
4. 证据不足时 fail-open，按 4-8 KiB 逐档扩读。
5. 强制保护条件、否定、数字、状态码、字段、代码符号和完整判断表行。

实现仅修改 Skill 规则，不增加运行时模型和 CLI 依赖。

## 评测对象

知识库：`/home/xch/goprojects/src/chat/apps/chat/.repomind`

当前人工知识规模：

| 类型 | 文件数 | 字节数 |
|---|---:|---:|
| concepts | 35 | 145,014 |
| modules | 48 | 247,357 |
| troubles | 135 | 577,733 |
| 合计 | 218 | 970,104 |

## 方法

选择 10 个覆盖支付、聚合标签、Viking memory、订阅奖励、Edge chat、角色编辑、签到、Lorebook、周活动和 Google 登录的真实问题。

对每个问题使用同一组已命中的 2-3 篇候选文档，比较：

- **优化前**：读取候选文档全文。
- **优化后**：保留 frontmatter，并按新 Skill 规则投影最小充分章节。

投影规则：

- concept：`是什么`、相关 `核心规则`、必要的 `易混淆概念`。
- module：`模块职责`、相关 `关键代码`、必要的 `AI 注意事项` 和一个问题相关章节。
- trouble：`适用症状`、第一次分流所需的 `首查步骤`、命中的 `判断分支`、最小 `验证方式/修复原则`。

每个案例重复执行投影 200 次，记录本地处理中位耗时。评测衡量知识上下文大小和本地处理开销，不把字节下降直接伪装成远端模型端到端延迟；真实 TTFT 仍需在具体模型供应商上做线上 A/B。

## 结论

对 Chat 项目，单纯采用无模型的渐进式章节投影，已经可以在不改知识源、不破坏 Markdown 和判断逻辑的情况下，把送入模型的 RepoMind 知识上下文稳定减少约 **30%-58%**，样本综合值为 **41.4%**。

该收益发生在模型请求之前，本地开销低于 1 ms。实际回答加速将主要来自减少模型 prefill 输入；具体 TTFT、总响应时间和费用下降取决于所用模型、供应商 Prompt Cache、用户问题长度和后续是否触发证据扩读。

## 后续线上指标

若接入真实问答链路，建议记录但不持久化知识正文：

- 初始候选文件数。
- 初始知识字节数和最终扩读字节数。
- 扩读次数。
- 首 Token 延迟、总响应时间和输入 token。
- 因证据不足导致的二次读取比例。
- 回答引用的知识文件与章节。

线上 A/B 应同时检查回答正确率，不能只以 token 或延迟下降作为成功标准。

## Compact 协同规则

本次随后把同一套渐进式上下文约束加入 `repomind-compact`，使源文档主动形成适合 Query 投影的结构：

- Trouble 核心三节目标不超过 4 KiB，超过 6 KiB 必须继续压缩或拆分。
- Concept 初始投影目标不超过 4 KiB，Module 不超过 5 KiB。
- 判断分支必须原子化，完整保留条件、否定、结论和下一步。
- 长 SQL、完整命令和背景说明后置到同一 Markdown 的稳定详情标题下。
- 压缩验收增加初始投影字节数和“核心入口 + 详情标题”映射。

这些规则尚未重新改写 Chat 的 218 篇知识文件，因此 **41.43% 是当前实测值**，不是加入 Compact 协同后的预测值。下一轮实际运行整库 Compact 后，应使用同一组 10 个问题重新评测，才能确认额外收益。

## Summary 协同规则

`repomind-summary` 同步改为直接在当前上下文执行 gate，不再通过 `.query-findings.json` 或其他临时文件传递发现。写入采用增量优先策略：复用本轮已命中的知识文件，只读取目标章节，优先更新最小所有者章节，并按与 Compact 相同的投影预算、原子判断分支和详情后置规则自检。这样可以避免新沉淀的知识重新把 Query 上下文撑大。
