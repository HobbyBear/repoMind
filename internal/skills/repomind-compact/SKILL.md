# RepoMind 整库精简

目标不是缩短几个句子，而是把知识库从“AI 工作日志”改成陌生同事能顺序阅读的当前业务手册。

## 安全边界

- 只修改 `.repomind/project.md`、`.repomind/README.md`、`.repomind/concepts/*.md`、`.repomind/modules/*.md`、`.repomind/troubles/*.md` 和可重建的 `.repomind/.generated/`。
- 不修改业务代码，不执行 commit、push、checkout、reset、clean、stash。
- Git 历史保留演进过程；正文只保留当前有效事实。无法确认的新旧冲突写入最终报告，不猜测。
- 本流程产出审阅草案，发布权属于用户。

## 步骤 1：建立基线

依次执行 `repomind kb-build`、`repomind kb-audit`，记录总文档数、总字节、错误、警告、超长页、新人检索结果。读取 `project.md` 和 `.generated/catalog.json`，再分批完整读取所有人工 Markdown；不能只看 metadata。

## 步骤 2：逐条裁决

每条内容必须明确归入一种处理，不允许默认追加：

- `KEEP`：当前仍有效、代码不容易直接看出、对后续读者可复用。
- `REPLACE`：新结论修正旧结论；正文只留新结论，Git 保存旧版本。
- `MOVE`：事实放错了所有者；移到唯一主文档，其他位置只保留链接和一句上下文。
- `DISCARD`：过程日志、一次性 ID、原始报错堆栈、完整调查时间线、代码可直接读出的细节、重复表述。

唯一所有者规则：业务定义和规则归 `concepts`，模块职责、入口和改动风险归 `modules`，可复用的症状、判断顺序、根因和验证归 `troubles`。同一事实不得在多篇复制。

## 步骤 3：先修新人入口

`project.md` 必须让完全没接触过项目的人在五分钟内回答：系统服务谁、解决什么问题、主流程是什么、有哪些一级能力、边界是什么、下一步该读哪几篇。先讲业务语言，再给代码入口；首次出现的领域词要解释，不以文件名和函数名代替概念。

每篇正文首屏应回答“这是什么、什么时候看、最重要的结论”。使用短段落、表格或列表组织规则；不要写“本次新增/某日调整/排查过程中发现”式日志。

## 步骤 4：压缩、合并与拆分

- `description` 不超过 120 字，只用于判断是否应打开本文。
- 不得用脚本、固定字符截断或省略号批量裁切 `description`。必须重写成语义完整的路由句，至少保留“本文是什么/出现什么症状”和“何时打开”。
- `keywords` 保留 3-8 个真实搜索词，删除泛词、长句和同义堆叠。
- 页面以 8 KiB 为建议上限，超过 12 KiB 必须缩减或按独立业务主题拆分。
- 单章节以 2 KiB 为建议上限，超过 4 KiB 必须拆分。
- 相同意图的短文合并；混合多个独立意图的大文拆分。不要为了数字机械拆成碎片。
- 不得为了消除 warning 机械增加空洞章节、占位句或同义转述；结构校验通过后，正文仍必须比基线更容易阅读。
- 旧文件路径被删除时，在相关主文档加入“关联知识”，保证概念仍可发现。
- 超过 150 行的主文视为难以快速通读：将个案、修订记录和长故障过程移出，直到主文只剩稳定结论。
- 已作废但仍有历史价值的页面改为 `status: deprecated`；默认检索必须排除。纯测试页、空页和无业务价值页面直接删除。

## 步骤 4.5：消解冲突和术语

- 对跨文档冲突列出双方说法并查找现有证据；能确认时只在唯一主文档保留当前规则，其他位置改成链接。
- 冲突涉及当前默认链路、开关含义或代码行为时，允许只读检查最小源码/配置定义作为证据；不得仅凭两篇旧文档投票。环境实际灰度值无法从仓库确认时，明确标成“需运维/产品确认”，不要猜测。
- 证据不足时不得擅自二选一：在草案报告中列为人工确认项，并避免把任一说法包装成确定事实。
- `project.md` 必须包含“术语速查”和“推荐阅读顺序”，解释领域缩写、身份层级、货币/额度、系统边界词。
- 多条实现链路并存时，必须标注 `current / conditional / legacy / deprecated`，说明默认生产路径和切换条件；不能只堆调用链名称。
- 核心用户旅程至少有一条端到端流程，先用业务动作表述，再链接到 module 技术入口。

## 步骤 5：整库验收

再次执行 `repomind kb-build`、`repomind kb-audit`、`repomind kb-validate`。精简后的错误数、超长页数、总字节数均不得高于基线；如果仍有超硬限制文件必须继续处理。

验收时 `description_incomplete`、`generic_description`、`revision_log` 和 `placeholder_description` 必须为 0；不能用总 warning 已下降掩盖机械摘要或日志残留。

至少执行这些新人检索回归：

```bash
repomind kb-search --query "这个系统是做什么的，新人应该先看什么" --limit 5 --expect project.md
repomind kb-search --query "核心业务流程和模块怎么协作" --limit 5 --expect project.md
```

最终只输出：基线与结果指标、修改/合并/拆分/删除文件清单、仍需人工确认的冲突。不要提交或推送。
