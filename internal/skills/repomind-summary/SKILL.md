# RepoMind 编码后总结

## 步骤 1：Summary Gate

Gate 直接使用本轮已经获得的用户确认、代码证据、验证结果和知识上下文。不得为了在 Query 与 Summary 之间传递状态而创建临时 JSON、发现文件、任务文件或后台流程；平台不能嵌套调用 Skill 时，就在当前上下文继续执行本文步骤。

只有同时满足以下条件才写入：

1. **新颖**：现有知识没有完整覆盖，或旧结论已过时。
2. **业务相关**：属于业务定义、模块约束、排查方法或需求意图，不是普通源码事实。
3. **可复用**：未来同类问题仍有价值，不是当前任务流水账。
4. **已确认**：来自用户确认、当前代码、工具结果或验证结果；猜测必须标明证据强度。
5. **可执行**：能说明适用场景、判断依据以及下一步动作。

以下情况直接判定无需写入：

- 仅做格式、命名、依赖或机械重构。
- 内容在代码中可以快速直接读出，且没有隐含业务原因。
- 裸日志、原始报错、一次性 ID、精确日期、Owner、deadline、当前处置状态。
- 自动恢复且没有可复用诊断路径的瞬态问题。
- 未验证的建议、担忧或假设。

如果用户明确要求“记一下”“沉淀经验”或纠正旧结论，gate 默认通过，但仍要按正确类型归档和压缩。

Gate 不通过时立即停止知识写入，不重新扫描仓库，也不为了输出总结而创建任何文件。

## 步骤 2：归类发现

每条发现只归入一个主要所有者：

- `concept_knowledge`：业务定义、存在目的、稳定规则、边界和易混淆概念。
- `module_knowledge`：模块职责、稳定入口、常见修改场景、影响面和隐性约束。
- `trouble_knowledge`：可复用症状、公共首查步骤、证据分支、修复原则和验证方式。
- `discard`：无法脱离当前事件独立理解，或没有长期价值。

同一事实不得在多篇文档复制。其他文档只保留链接和必要上下文。

## 步骤 3：渐进式选择目标

使用平台原生文件搜索和读取能力：

1. 先用本轮已经命中的知识文件作为候选，不重复搜索。
2. 候选不足时，只扫描对应目录 Markdown 的 frontmatter 和标题。
3. 按 `code_refs`、`name`、`description`、`keywords`、标题的顺序选择 1-3 个候选。
4. 先读取可能承载增量事实的目标章节；只有无法裁决时才打开候选全文。
5. 选择文档动作：

| 动作 | 条件 |
|---|---|
| `SKIP` | 已完整覆盖，新增内容没有增量或证据更弱 |
| `UPDATE` | 同一事实的新结论更具体、更新或更权威 |
| `MERGE` | 同一工作对象或诊断入口，信息互补且不冲突 |
| `CREATE` | 候选都不是同一对象，并能说明无法合入的原因 |

默认优先 `UPDATE/MERGE`，不要因关键词相同就合并。`UPDATE` 只改动拥有该事实的最小章节，不无理由重写整篇文档。

## 步骤 4：Trouble 二次准入

通用 gate 通过不代表一定创建 trouble。候选经验还必须满足：

1. 能描述可重复出现的症状族和不适用边界。
2. 至少有一个可观察证据和对应下一步。
3. 能归纳公共首查入口，而不是复述一次事故。
4. 与已有 trouble 不属于同一“症状族 + 业务对象 + 公共首查入口”；属于同一入口时必须合并为判断分支。
5. 内部复用价值低于 70/100 时丢弃，不把分数写进正文。

事故本身可以丢弃，但其中稳定的判断方法、禁止做法和验证方法应先尝试升维提炼。

## 步骤 5：按固定结构写入

所有文档必须包含：

```yaml
---
name: "..."
description: "..."
status: active
keywords: []
code_refs: []
---
```

### concepts

必备章节：`是什么`、`核心规则`。可选：`适用场景与边界`、`关联知识`。

### modules

必备章节：`模块职责`、`关键代码`。可选：`常见修改场景`、`关键约束`、`AI 注意事项`、`关联知识`。

技术入口优先写稳定函数、方法、类型或接口，并同步到 `code_refs`；不保存行号。

### troubles

必备骨架：

```markdown
## 适用症状
## 首查步骤
## 判断分支
| 证据或条件 | 结论 | 下一步 |
|---|---|---|
```

`修复原则`、`验证方式`、`容易误判` 和 `关联知识` 只有确有跨案例价值时才添加。首屏必须完成症状确认和第一次分流。

判断分支必须原子化：每行独立保留完整的“证据或条件 → 结论 → 下一步”。错误码、状态、字段、阈值、时间窗口以及“不、不得、仅、必须、除非、不适用”等条件和否定必须留在对应分支，不能依赖“同上”或后置详情补全结论。

## 步骤 6：写入时同步压缩

每次更新都必须顺手压缩目标文件，而不是只追加：

1. 删除修订记录、调查时间线、真实 ID、日期案例、Owner、当前状态和重复结论。
2. 新结论替换旧结论；历史交给 Git，不在正文保留双版本。
3. 把同一意图的散句合并为规则、步骤或判断表。
4. 把放错所有者的内容移动到正确类型；范围外无法移动时只保留待处理说明。
5. 保留表名、关键字段、状态码、稳定代码符号和必要命令等证据锚点。
6. 更新正文后同步收紧 `description`、`keywords` 和 `code_refs`。
7. 核心结论写入初始投影章节；长 SQL、完整命令、扩展背景和完整数据流后置到同一 Markdown 的稳定详情标题下。
8. 详情中的稳定事实必须从核心正文保留一句入口，说明何时展开对应标题；不得复制同一事实形成双份正文。

体积门槛统一为：

- `description` 不超过 120 个字符。
- `keywords` 最多 8 个，单个不超过 32 个字符。
- 文件超过 8 KiB 必须在本轮继续精简或形成拆分；超过 12 KiB 必须立即拆分，不能只留计划。
- 单章节超过 2 KiB 必须继续精简或拆小节；超过 4 KiB 必须立即拆分。
- 超过 150 行时优先删除事件档案、重复说明和低价值过程。
- Trouble 的 `适用症状 + 首查步骤 + 判断分支` 目标不超过 4 KiB；超过 6 KiB 必须继续合并公共步骤、缩短分支或按独立诊断入口拆分。
- Concept 初始投影目标不超过 4 KiB；Module 初始投影目标不超过 5 KiB。

拆分时按独立业务概念、模块职责或诊断入口拆分。每篇新文档必须有独立 `name/description/keywords/code_refs`；原主文档保留关联链接，避免旧入口失效。

## 步骤 7：直接自检

逐个重新读取本轮新建或修改的完整文件，并确认：

- frontmatter 完整，`status` 合法，active 文档没有“待补充”占位。
- 必备章节存在且有实际内容，没有为了模板制造空章节。
- trouble 至少有一个有效判断分支；每个分支都有证据、结论和下一步。
- trouble 判断分支能够独立理解，条件、否定、结论和下一步没有拆散到其他章节。
- 没有修订记录、事件时间线、真实业务 ID、当前状态和重复内容。
- `description/keywords/code_refs` 与当前正文一致。
- 文件和章节没有超过硬限制；超过软限制时已在本轮完成压缩或拆分。
- 初始投影章节位于详情之前，只读取初始投影即可理解概念、模块职责或完成 trouble 首次分流。
- 进入详情的稳定事实保留了“核心入口 + 详情标题”映射，最终结论没有只存在于详情中。
- 修改没有越出用户授权范围。
- 本轮没有创建中转 JSON、临时发现文件或后台任务。

自检失败时继续修改，直到通过后再结束 summary。

## 步骤 8：输出摘要

最终摘要说明：

- Summary gate 是否通过及原因。
- 每条发现执行了 `SKIP/UPDATE/MERGE/CREATE/DISCARD` 中的哪一种。
- 修改、新建、拆分或删除了哪些知识文件。
- 删除了哪些事件性、重复或过时内容。
- 保留了哪些关键证据锚点。
- 初始投影是否达到 Concept 4 KiB、Module 5 KiB、Trouble 核心三节 4 KiB 的目标。
- 是否仍有范围外待确认项。
