# RepoMind 编码前 / 问答分析

## 核心原则

1. RepoMind 的知识源是 `.repomind/concepts/**/*.md`、`.repomind/modules/**/*.md` 和 `.repomind/troubles/**/*.md`。
2. 先只读取 frontmatter 和标题，选出少量候选；不要先扫完整正文。
3. 默认只使用 `status: active`；只有用户明确要求草稿或历史结论时才读取 `draft` / `deprecated`。
4. 候选优先级为 `code_refs` 精确符号、`name`、`description`、`keywords`、正文标题。
5. 每个激活的知识类型最多打开 1-3 篇正文；证据足够后立即停止扩展读取。
6. 平台原生文件搜索、文本搜索和文件读取已经足够，不调用 RepoMind CLI、生成目录、缓存索引或外部图谱。
7. 回答完成前直接执行本文末尾的 summary gate；不创建中转 JSON，也不把总结推迟到下一轮。

## 步骤 1：识别问题维度

| 维度 | 典型问题 | 首选知识 |
|---|---|---|
| 业务概念 | 是什么、为什么、边界、区别、预期 | `concepts` |
| 代码模块 | 在哪改、入口、影响面、注意事项 | `modules` |
| 异常排查 | 为什么没生效、数据异常、如何验证 | `troubles` |
| 业务纠错 | 用户修正事实、模块归属、入口或根因 | 被纠正的原文档 |

只检索与已激活维度有关的目录。不要为了覆盖率读取整个知识库。

## 步骤 2：只读 frontmatter 选候选

使用当前平台的原生文件搜索和读取能力：

1. 列出目标目录内的 Markdown 文件。
2. 只读取每个文件开头的 YAML frontmatter 和一级、二级标题。
3. 按下列顺序判断相关性：
   - 用户问题包含完整 `code_refs` 或稳定符号名。
   - `name` 与业务对象或模块名称一致。
   - `description` 覆盖当前场景、症状或影响面。
   - `keywords` 包含常见别称、缩写或入口词。
   - 正文标题覆盖用户要问的主题。
4. 每种知识类型只保留最相关的 1-3 篇。

frontmatter 缺失或状态不明确的文件不作为默认答案依据，但可以列为待整理项。

## 步骤 3：按维度读取正文

### concepts

只提取：

- 业务定义和存在目的
- 适用场景与边界
- 核心规则
- 易混淆概念

### modules

只提取：

- 模块职责
- 包含能力
- 技术入口及入口用途
- 关键约束、影响面和常见修改场景

### troubles

只提取：

- 适用症状和不适用边界
- 公共首查步骤
- 证据对应的判断分支
- 修复原则、验证方式和高价值误判

排查记录是快速诊断指南，不是事故时间线。真实 ID、日期、Owner、当前状态和原始日志不能直接作为长期结论。

## 步骤 4：补最小代码证据

知识文档给出入口后，优先按 `code_refs`、函数名、类型名或业务词定位当前代码，并只读取命中附近的最小上下文。

- 当前代码与知识文档冲突时，以当前代码和用户确认的事实为准，并明确指出旧知识需要更新。
- 只把当前打开文件中直接出现的调用描述为局部调用证据。
- 没有穷尽证据时，不声称完整 callers、callees 或完整影响面。
- 代码证据已经足够回答时，不继续扩大源码读取范围。

## 步骤 5：形成回答

回答前确认：

- 哪些知识文档真正支撑了结论。
- 命中了哪些 frontmatter 字段和正文章节。
- 哪些结论来自当前代码或用户确认。
- 是否存在冲突、缺口或证据不足。

业务结论必须来自 concept、用户确认或当前代码；代码位置必须来自 module 与当前代码；排查建议必须来自 trouble 或本轮形成的明确证据路径。

## 步骤 6：直接执行 Summary Gate

最终答复前在当前上下文判断是否出现以下新知识：

- 现有概念文档没有覆盖的业务规则或边界。
- 现有模块文档缺失的稳定入口、常见修改场景、影响面或检索词。
- 可跨案例复用的新症状、判断证据、根因分支、修复原则或验证方法。
- 用户明确纠正了已有知识。

没有新知识时，明确判定“无需更新”，然后回答用户。

有新知识时，立即执行 `repomind-summary` 的完整流程；若平台不能嵌套调用 Skill，就在当前上下文直接完成其 gate、候选选择、合并、压缩和自检步骤。不得创建中转文件，也不得把 summary 描述成后台任务。
